# Taro research on assets, motion, and interactive 3D

15 November 2026

Give two reference projects equal weight. Build an editorial feature whose photography, typography, and narrative hold up on a phone, and a product showcase whose 3D model can be explored and understood with touch, mouse, or keyboard. Use the same asset records and preview workflow in both. The sources below were read or inspected upstream. The linked demos and source files are model code for the implementation. No upstream example was executed during this review.

Keep the project identity there, and attach specific assets and story beats to the design job that uses them. ## Project Assets workflow

- When a design job runs in its approved Git worktree, Taro copies the registered assets named by the approved direction, typography, and scene. It preserves each selected original, the approved version and its source lineage, and a linked preview image or poster. Use the recorded relative paths from the worktree's local server to verify those files in the implementation preview.
- In Gallery → Project assets → Generate an image, save a Google Gemini API key in the operating-system credential store. Enter a description to generate a candidate. For edits, choose a PNG, JPEG, or WebP version and use Add a version → Edit image with Gemini. The command sends that version and the instruction to Google. The backend uses the Interactions API with server-side interaction storage disabled. It records the model, instruction, and source version with the output. Set `TARO_GEMINI_IMAGE_MODEL` before starting Taro to use a different Gemini image model. [Google's image generation and editing guide](https://aistudio.google.com/docs/image-generation)
- To create a WOFF2 subset, install FontTools with Brotli using `python -m pip install "fonttools[woff]"`. Taro uses Python from PATH or an absolute interpreter path in `TARO_ASSET_PYTHON`. In Add a version → Subset font to WOFF2, use the page copy covered by the font's permissions. The resulting WOFF2 previews using that copy and can travel with the workspace. [FontTools subset documentation](https://fonttools.readthedocs.io/en/stable/subset/)
- Add a version → Compact GLB losslessly repacks an embedded GLB buffer, removing gaps and reusing identical aligned buffer views. It preserves geometry, scene node names, and material and animation data. It saves a version only when the file is smaller. For Meshopt, Draco, and other codecs, import a prepared GLB as a compressed version and configure the decoder in the target site. [glTF Transform CLI documentation](https://gltf-transform.dev/cli)
- To exercise the asset workflow in Edge or Chromium, build the native `project_assets_smoke` example with `cargo build --manifest-path src-tauri/Cargo.toml --no-default-features --example project_assets_smoke`, then run `node scripts/project-assets-browser-check.mjs`. Set `TARO_ASSET_SMOKE_FONT_SUBSET=1` to include real WOFF2 subsetting with the configured Python. The browser smoke uses a controlled provider error for generation and editing.

## Fourteen source references and code models

1. **Responsive photography and art direction.** MDN’s complete HTML demo contains both a picture element that chooses a tight or wide crop according to viewport width and an image that supplies two same-crop widths with source-selection hints. Adopt those browser primitives. Adapt the breakpoints to the available column width, define real intrinsic sizes, give meaningful images useful alt text, and source project-owned or appropriately licensed photography. The demo header names an outside photographer, so the example code and its image are separate reuse decisions. [Live example](https://mdn.github.io/learning-area/html/multimedia-and-embedding/responsive-images/responsive.html) · [HTML source](https://github.com/mdn/learning-area/blob/main/html/multimedia-and-embedding/responsive-images/responsive.html#L47-L64) · [MDN guide](https://developer.mozilla.org/en-US/docs/Web/HTML/Guides/Responsive_images)
2. **Local image derivatives with Sharp.** The maintainer’s examples show fit/gravity, attention crop, trim, and file or buffer output for WebP and AVIF. Adopt local resize, trim, and encode as repeatable transforms. Accept an explicit focal point and explicit desktop/mobile crops. An automatic crop can suggest a starting point. Preserve transparency on cutouts and preserve the input for later edits. Sharp trim removes edge pixels and can refine framing after segmentation. To use an authored focal point, store normalized x/y on the original, calculate and clamp one crop rectangle for each aspect ratio, pass its integer left, top, width, and height to Sharp's extract operation, then resize. [Resize and trim examples](https://sharp.pixelplumbing.com/api-resize/) · [Explicit crop code](https://sharp.pixelplumbing.com/api-resize/#extract) · [Encoder examples](https://sharp.pixelplumbing.com/api-output/)
3. **Image generation and editing.** Google’s provider guide includes JavaScript examples for text-to-image and text plus image editing. The current example uses the @google/genai SDK with ai.interactions.create. It sends the generation prompt as text, or for editing sends a text instruction along with a typed base64 image. It reads the generated bytes from output_image.data. Use a configured model and backend-held credential. The first-party cookbook also provides an Apache-2.0 JavaScript file with the earlier generateContent API and iterative editing. Adapt the request/response pattern into a provider adapter with stored source asset IDs, model, prompt or edit instruction, configured aspect ratio, generated output, and revision. Treat provider outputs as candidates for review. Use the owner’s product photos or approved renders where logos, fabric, fit, or product geometry must be accurate. Specific provider terms and output rights were outside this source review. [Google Interactions API generation and editing examples](https://aistudio.google.com/docs/image-generation) · [Google cookbook JavaScript source](https://github.com/google-gemini/cookbook/blob/main/quickstarts-js/Image_out.js)
4. **Transparent product cutouts.** Rembg’s Python usage and implementation show mask-only output, alpha matting, post-processing, and background replacement. Trial the mask-and-cutout pattern behind an optional processing adapter. Choose the model explicitly and retain both mask and alpha output for correction. Test dark and light backgrounds, soft edges, hair, translucent material, and shadows. The Rembg code is MIT. Its model weights carry separate terms, so the selected weights require their own verification before shipping. [Usage examples](https://github.com/danielgatis/rembg/blob/main/USAGE.md) · [Mask implementation](https://github.com/danielgatis/rembg/blob/main/rembg/bg.py#L255-L340) · [Code license](https://github.com/danielgatis/rembg/blob/main/LICENSE.txt) · [Model-license note](https://github.com/danielgatis/rembg)
5. **Stock photo and video intake.** Pexels’ JavaScript API examples and documentation provide a source for candidate photos and videos. Adapt search and source linking only where the integration fits their documented terms. Retain creator, asset page, license, and usage restrictions. Keep direct upload and manual import first-class. Store the approved derivative locally where terms allow and avoid using the provider’s catalog as a redistributable fixture collection. [Provider API examples](https://www.pexels.com/api/documentation/?language=javascript) · [Asset license](https://www.pexels.com/license/) · [Terms](https://www.pexels.com/terms-of-service/)
6. **Self-hosted type.** Fontsource documents CSS imports by weight and style, with explicit subsets as an option. Taro already imports variable Geist and both ordinary and italic Instrument Serif at weight 400 in its entry point. Adopt that pattern and ship only the WOFF2 files and weights the target needs. Let the generated unicode-range rules select scripts unless the project calls for an explicit subset. Verify fallbacks, accented characters, and mobile wrapping. Instrument Serif and Geist are listed under OFL-1.1. A customer brand font needs a web-use permission record for the specific files. [Fontsource import examples](https://fontsource.org/docs/getting-started/install) · [Taro font imports](A:/taro/src/main.tsx:3) · [Instrument Serif license](https://fontsource.org/fonts/instrument-serif) · [Geist license](https://fontsource.org/fonts/geist)
7. **Video playback and posters.** The web.dev implementation examples show a video poster, preload behavior, and deferred requests. FFmpeg documents scaling and thumbnail selection. Adopt a separate poster and explicit user playback for editorial video. Adapt a per-project offline processing step for poster extraction and encodes if needed. Give speech captions and preserve a readable page with the video unavailable. FFmpeg describes LGPL and GPL builds depending on enabled components, so check the chosen distribution before any bundling decision. [Browser examples](https://web.dev/learn/performance/video-performance) · [FFmpeg filters](https://ffmpeg.org/ffmpeg-filters.html) · [FFmpeg license](https://ffmpeg.org/legal.html)
8. **Environment maps and textures.** Poly Haven lists studio HDRIs, material textures, and models with source authors, resolutions, formats, and CC0 asset licensing. Its API docs include sample metadata for IDs, files, creators, and hashes. Adapt this as an import reference. Use a deliberately low-resolution, local lighting asset or authored lighting for the first 3D recipe. The supplied Studio Small 03 page offered an EXR download at 21.9 MB in its displayed configuration, which illustrates the need to choose resolution and measure bytes. Asset license and live API terms are distinct. The individual files API endpoint could not be inspected through the web tool. [Studio Small 03](https://polyhaven.com/a/studio_small_03) · [Texture example](https://polyhaven.com/a/concrete_floor_01) · [Asset license](https://polyhaven.com/license) · [API examples and terms](https://polyhaven.com/our-api)
9. **Optimize GLBs before delivery.** The glTF Transform CLI examples show optimize, inspect, mesh compression, texture resizing and GPU-ready KTX2 treatments. Adopt the inspection-and-derivative flow. Compare an uncompressed reference against a compressed rendition and measure network size, load/decode time, texture memory where observable, fidelity, and preservation of names or interactions. Select Meshopt or Draco and texture formats from the capabilities of the actual viewer. Preserve material slots, animation clips, and hotspots the design depends on. MIT license for the tool. [CLI code examples](https://gltf-transform.dev/cli) · [MIT license](https://github.com/donmccurdy/glTF-Transform/blob/main/LICENSE.md)
10. **Compact product inspection with model-viewer.** The staging demo implements orbit, target, native vertical swiping on touch, and optional zoom restriction. The loading example implements both poster-first and manual reveal. The scene-graph example changes a shoe model’s embedded variant from a control. Trial the component in the product recipe when orbit, material choices, and a few hotspots cover the experience. Use semantic buttons for load and variant controls, leave page scrolling available, and keep an independent HTML poster and product information if the renderer fails. The examples are Apache-2.0, with independent asset licenses. The staging page lists its damaged helmet model under CC BY-NC, so use owned or cleared replacements. The loading guide notes separate decoder requests for compressed models. Count and pin or locally serve those with the rest of the recipe where supported. [Camera live demo and credits](https://modelviewer.dev/examples/stagingandcameras/) · [Camera example source](https://github.com/google/model-viewer/blob/master/packages/modelviewer.dev/examples/stagingandcameras/index.html) · [Loading example source](https://github.com/google/model-viewer/blob/master/packages/modelviewer.dev/examples/loading/index.html) · [Material variants source](https://github.com/google/model-viewer/blob/master/packages/modelviewer.dev/examples/scenegraph/index.html) · [Loading and codecs](https://modelviewer.dev/examples/loading/)
11. **Custom Three.js scenes with React Three Fiber and Drei.** R3F’s GLTF demo loads alternative models under a suspense boundary. Its scaling guide contains on-demand rendering, explicit frame invalidation, and adaptive quality examples. Drei’s Environment sets the reflections/background from a project file, ScrollControls exposes damped progress, and PerformanceMonitor records frame timings and calls quality-change callbacks. Adopt R3F when the experience needs a coordinated camera path, multiple objects, part animation, custom lighting or particles. Adapt the loader to keep a real poster during suspense and failure. Prefer native page scroll with a sticky scene and one progress source for the editorial site. Use Drei ScrollControls where an isolated viewer actually needs its own scroller. Drei warns that its remote environment presets are for convenience. Use tracked local files for shipped artifacts. R3F and Drei repositories indicate MIT licensing. [GLTF loading source](https://github.com/pmndrs/react-three-fiber/blob/master/example/src/demos/Gltf.tsx) · [R3F scaling examples](https://r3f.docs.pmnd.rs/advanced/scaling-performance) · [Drei Environment docs](https://drei.docs.pmnd.rs/staging/environment) · [Drei ScrollControls source](https://github.com/pmndrs/drei/blob/master/src/web/ScrollControls.tsx) · [Drei PerformanceMonitor source](https://github.com/pmndrs/drei/blob/master/src/core/PerformanceMonitor.tsx) · [R3F license information](https://github.com/pmndrs/react-three-fiber) · [Drei license](https://github.com/pmndrs/drei/blob/master/LICENSE)
12. **Budgeted particles.** Three.js’ official sprite demo fills one buffer geometry with positions and reuses it across point groups with different sprite, size, and color parameters. Adapt the buffer-based approach and use seeded positions for reproducible captures. Choose modest counts per quality tier, bound pixel ratio and blending cost, and suspend the simulation outside the viewport. The demo’s full-device pixel ratio and overlapping additive layers deserve measurement on actual phones. The Three.js code license is MIT. Independent sprite asset rights were unverified. 13. **Scroll, reduced motion, and structured choreography.** Motion’s examples show scroll progress, mapped transforms, and reacting to reduced-motion preferences. ## Plan and checks in plain language

First, take one responsive editorial feature and one interactive product viewer from imported assets through the same plan, preview, and QA workflow. Expand into generated and edited assets, reusable recipes, and custom 3D scroll, lighting, and particle scenes after that workflow is repeatable. Keep a visible editorial and interactive 3D deliverable at each milestone.

### 1. Give every project an asset list

Accept files supplied by the user, licensed online media, and generated assets when the job calls for them. Add simple edit actions for crop, background removal, poster extraction, and optimization. Keep the original, each chosen derivative, and a preview of its intended use. Give the designer a short brief for each placement covering subject, framing, fidelity constraints, mobile crop, and placement. For editorial imagery, generation can fill a visual gap. For commerce, use approved item photography or measured models for identifying item details. Keep provider credentials and private inputs out of exported previews.

Each asset entry should carry stable ID, revision, project-relative path, byte count, content hash, MIME type, kind, source and creator, provenance, rights/attribution and use limits, and the pages or scenes using it. Add dimensions/duration, alpha/mask relationship, font weight/subset, or GLB geometry and texture details where useful. Record how a derivative was made, including the generation model or transformation settings. A revision records the specific rendition choices used in preview and export. Report unverified rights visibly on the candidate before shipping decisions.

**Acceptance.** Import one original of each relevant type, generate or edit an image, produce a cutout and responsive hero crops, optimize and inspect a GLB, and link a lighting map and texture. Look up each asset’s origin, rights, size, and where it is used. Reload and export the project, then open it without the original provider connection. Confirm the browser selects the intended crop and sees no unsupported asset paths. On retry the same input and transform should reuse the matching derivative, with older revisions still resolving their own files.

### 2. Ship an editorial page that works in still and animated forms

Make a real feature with a lead photograph and strong mobile crop, typographic hierarchy, running text, a photo detail or paired gallery, a poster-backed video, and one motion sequence that clarifies the story or reveals a detail. Set type and spacing through the saved project style. Start with native page scrolling and one short motion sequence. Design the reduced-motion layout and the video’s readable substitute with the rest of the page.

**Acceptance.** At phone and desktop widths the main subject remains visible and text is readable at ordinary and enlarged settings. Confirm the correct image variant arrives without shifting the page, key content appears while video is blocked, controls are keyboard operable, captions are available, and turning on reduced motion removes parallax or scrubbing while preserving all content and actions.

### 3. Ship a product inspector and a choreographed 3D section

Start with a poster, a clear invitation to explore, a user-controlled orbit, two labeled finishes, one reset action, and a couple of detail angles with descriptive text. Use the simpler viewer for product inspection if it meets the spec. Build a custom editorial scene for the cases that require a timed camera move, multiple objects, controlled reflections or lighting, and particles. Specify whether effects support the story or are ornamental. Keep the view responsive, and give coarse pointers and keyboard controls real alternatives to dragging.

A clothing viewer, animated mannequin, swatches, and a simulated preview deliver visual presentation. Actual virtual try-on requires a separate implementation plan for user imagery or body tracking, garment mapping or simulation, fit accuracy, and data handling.

**Acceptance.** Activate 3D by keyboard and touch, change the finish, see the active state, reset orientation, and read product details without dragging. Test a phone swipe over the model, rotate the device, block the GLB, disable WebGL, and exercise reduced motion. The poster, details, and purchase or exploration flow remain available. In the custom scene check the beginning, middle, and end in both directions, plus a pause or static form for motion-sensitive visitors. Test with local files and include a corrupt asset fixture.

### 4. Have Designer describe beats that Code and QA can open

Keep an optional versioned scene-and-motion handoff alongside the current brief, layout, and design tokens. Describe the basic experience and fallback in words. Store precise values for implementation and evidence. A target is a stable layer or scene object ID rather than whatever selector happens to exist in a prototype. Each beat has a stable name, trigger, start/end time or normalized scroll range, property tracks, keyframes and easing, and the expected visible result. Use the same IDs and named checkpoints in preview and QA. Keep seconds or normalized progress explicit and avoid two controllers writing the same property.

Describe a scene with source model IDs and variants, node/target IDs, units and bounds, transforms, camera position/target/FOV, environment and rotation, direct lights and intensities, material properties and texture/color-space roles, render quality tiers, and fallback poster and text. Give desktop, touch, and reduced-motion behavior a concrete specification. Validate ranges, file references, unique target IDs, consistent units, bounded keyframes, and transform/material types. Store data and resolve it through known handlers. Let implementation code take over when custom logic is required.

Example of one checkpoint in ordinary language. At 45% of the story section, the camera settles on the stitching detail, a labeled caption is visible, and the environment still defines the main reflection. In the reduced-motion version that checkpoint is a still photograph with the same caption. QA can jump directly to both versions and verify the right detail.

**Acceptance.** Save and reload a job created before this feature and one using the new handoff. Load the exact saved scene and asset revisions in Code and QA. At each named checkpoint record a screenshot and relevant camera/material state. Reject an orphaned track, missing asset, out-of-range interval, or mismatched material ID before preview. Changing the prescribed shoe color or camera target creates a new reviewable revision.

### 5. Make the examples runnable and measurable

Give each recipe a readable description, preview link, screenshot or poster, launch and build instructions, pinned dependencies, local approved assets, documented inputs, fallback behaviors, license/credit notices, and an automated interaction or evidence check. Publish the responsive photo feature and product viewer with variants first. Follow with the motion-led editorial feature with captioned video and the 3D scroll scene with lighting and bounded particles. Parameterize the asset and story choices so unrelated brands can produce distinct pages from the same pattern. Record recipe version with the job when selected.

Choose and record budgets for each recipe as project decisions. Measure the first-view image and font bytes, JavaScript transferred before first interaction, additional video/model/texture/decoder bytes, loading times, and frame timings on a named phone profile. Start on a light quality setting, reduce render resolution/shadows/particles when the scene is slow, render resting views on demand, and stop render work when the scene is hidden. Keep a visible poster or still sequence for slow networks, unavailability, and reduced motion as appropriate. Compare screen captures and timing logs for release candidates.

**Acceptance.** From a fresh checkout, each recipe can load the documented assets and be previewed from its code. The poster and core text appear before deferred 3D or video downloads. Recovery states remain readable and a hidden scene stops spending regular frame time. At a small viewport, with reduced motion and no WebGL, the editorial information and product details remain intact. At the chosen thresholds record the actual measured bytes, frame timings, and captures alongside the revision. Re-run with a different project’s assets to ensure styles and scenes adapt without hard-coded paths or original brand copy.

Provider features, rights documentation, renderer integration, and mobile behavior need verification against the specific options chosen for implementation. The reference reading establishes patterns and source paths. Implementation should supply build, browser, and real-device evidence for the shipped recipe versions.
