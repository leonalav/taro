# Browser review and visual evidence for Taro

Research checked 2026-11-15. The examples below are upstream documentation and source reviewed during research. The implementation steps are recommendations for Taro. No upstream examples or Taro browser tests were executed for this note.

## What Taro has today

- Review mode opens HTML and URLs in a temporary headless Chromium profile. The same Node helper serves the packaged desktop app through a private Rust bridge and development through the Vite server. The helper already sends real mouse clicks, wheel events, text insertion, and a limited set of keys. The Prototype canvas calls those operations. Agents currently have preview, inspect, resize, audit, and comment tools. See [Review mode](A:/taro/docs/review-mode.md), [the browser helper](A:/taro/scripts/review-browser.mjs:104), [the request contract](A:/taro/src/lib/review-browser.ts:5), and [the tool definitions](A:/taro/src/lib/review-tool-definitions.ts:4).
- A capture currently waits two animation frames, reads DOM geometry, and takes a viewport PNG. The WebSocket handler only processes replies to commands. It currently drops unsolicited browser events, which is where error messages, failed requests, animation starts, and screencast frames would arrive. The helper serializes requests, and the browser and desktop transports both have 45-second request timeouts. See [the capture and command handling](A:/taro/scripts/review-browser.mjs:104), [the web transport](A:/taro/src/lib/review-browser.ts:12), and [the desktop bridge](A:/taro/src-tauri/src/review_browser.rs:37).
- Saved revisions already hold source, observations, screenshots, and visual audit reports. The audit covers eight combinations of theme and environment and records observations that need manual attention. Live captures and interaction state are separate. The larger development storage path still serializes entire sessions, which matters when deciding where to store recordings. See [the verification loop](A:/taro/docs/artifact-design-system.md:27), [the revision store](A:/taro/src/lib/review-store.ts:11), and [browser evidence storage](A:/taro/src/lib/review-evidence-storage.ts:5).

## References and model code

1. **Chrome DevTools Protocol** is the direct reference for the bridge Taro already has. The command schema defines pointer and key input, content bounds and clipped capture, console and exception events, request completion/failure, trace data, and screencast frame acknowledgement. Adapt the smallest commands needed and route events by the attached target session. Protocol tip-of-tree includes experimental features, so detect availability on the installed Chrome or Edge and surface unsupported operations. [Input](https://chromedevtools.github.io/devtools-protocol/tot/Input/), [Page](https://chromedevtools.github.io/devtools-protocol/tot/Page/), [Runtime](https://chromedevtools.github.io/devtools-protocol/tot/Runtime/), [Network](https://chromedevtools.github.io/devtools-protocol/tot/Network/), [Tracing](https://chromedevtools.github.io/devtools-protocol/tot/Tracing/).
2. **Chrome DevTools MCP** is the closest agent-facing example. Its input handlers resolve a page snapshot element identifier, keep coordinate click available, perform hover and key presses, and return observations after actions. Its screenshot tool validates element capture against full-page mode and remeasures the target rather than reusing old bounds. Its console and network tools paginate observations, and its performance tool starts and stops a trace with explicit state and cleanup. Adapt these scopes and result contracts to Taro's existing preview and revision IDs. The implementation uses Puppeteer and can expose raw request data, so its runtime dependencies and payloads are a poor fit for a direct port. Verified Apache-2.0. [Tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md), [input handlers](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/src/tools/input.ts#L183), [screenshot handler](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/src/tools/screenshot.ts#L201), [console](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/src/tools/console.ts), [network](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/src/tools/network.ts), [performance](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/src/tools/performance.ts), [license](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/LICENSE).
3. **Playwright** has good implementation and test examples for browser interaction and capture. `screenshotter.ts` serializes captures, distinguishes viewport and document rectangles, waits for fonts, and scrolls a visible element into position before measuring it. `page-drag.spec.ts` checks the actual event sequence and cancellation. Its actions guide explains why HTML drag-and-drop may need another move over the target before release. Adapt the edge cases for raw CDP, especially drag cleanup and converting CSS coordinates into image coordinates. Full-document images can still miss content that only mounts while scrolling, and an element image can show an overlay that covers the element. Verified Apache-2.0. [Screenshot implementation](https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/server/screenshotter.ts#L178), [drag tests](https://github.com/microsoft/playwright/blob/main/tests/page/page-drag.spec.ts#L25), [actions](https://playwright.dev/docs/input#drag-and-drop), [actionability](https://playwright.dev/docs/actionability), [license](https://github.com/microsoft/playwright/blob/main/LICENSE).
4. **Chrome Recorder and Puppeteer Replay** demonstrate a portable list of named steps. The Replay README validates saved JSON before running it and describes extension hooks for screenshots. `PuppeteerRunnerExtension.runStepInFrame` resolves targets, sets step deadlines, and starts waiting for expected events as actions occur. Adapt the idea as a short sequence with expected states and a result per step. The replay is only as repeatable as its initial data, selectors, timing conditions, and dependencies. Verified Apache-2.0 for Puppeteer Replay. [Chrome Recorder](https://developer.chrome.com/docs/devtools/recorder/), [Replay examples](https://github.com/puppeteer/replay#2-customize-replay), [runner implementation](https://github.com/puppeteer/replay/blob/main/src/PuppeteerRunnerExtension.ts#L80), [license](https://github.com/puppeteer/replay/blob/main/LICENSE).
5. **Playwright Trace Viewer and video recorder** demonstrate how to show a step list, before and after states, a time-ordered filmstrip, console messages, and network activity in one review. `videoRecorder.ts` shows timestamped frames, a separate FFmpeg encoder, and finalization. Chrome DevTools MCP's `screencast.ts` shows native Chrome recording and an FFmpeg-backed alternative, with an explicit unsupported-browser path. Adapt the viewer and begin with a bounded filmstrip. A video is a record of one run and its timestamps are observation times. A downloadable video needs an encoder or a supported installed browser recording path, size limits, and successful finalization. Verified Apache-2.0 for both example repositories. [Trace Viewer](https://playwright.dev/docs/trace-viewer), [video options](https://playwright.dev/docs/videos), [Playwright encoder implementation](https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/server/videoRecorder.ts), [DevTools MCP recording implementation](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/src/tools/screencast.ts), [Playwright license](https://github.com/microsoft/playwright/blob/main/LICENSE), [DevTools MCP license](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/LICENSE).
6. **Chrome Animations and the protocol schema** show the difference between live capture and browser-controlled scrubbing. `Animation.pdl` defines discovery, pause, seeking, and release for recognized animations. Chrome's animation panel demonstrates grouping and scrubbing CSS animations, CSS transitions, Web Animations, and View Transitions, and documents its lack of `requestAnimationFrame` support. Adapt explicit checkpoints for supported animations. Scroll-driven effects need scroll-position checkpoints or separately supported normalized progress. Browser seek does not advance arbitrary JavaScript or WebGL simulation state. [Chrome Animations](https://developer.chrome.com/docs/devtools/css/animations/), [protocol definition](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Animation.pdl).
7. **Three.js and the WebGL specification** document a controlled render before canvas export. `tips-screenshot-good.html` separates `render()` from its frame loop, then renders immediately before `canvas.toBlob()`. Adapt the separation for Taro-authored canvas or WebGL demos that deliberately expose a time or scene-state input and a ready signal. For existing third-party pages, prefer compositor screenshots and timed frames. Canvas readback has drawing-buffer lifetime constraints. Changing `preserveDrawingBuffer` would change the workload under review. Verified MIT for Three.js. [Example source](https://github.com/mrdoob/three.js/blob/dev/manual/examples/tips-screenshot-good.html), [Khronos drawing-buffer rules](https://registry.khronos.org/webgl/specs/latest/1.0/#5.2), [Three.js license](https://github.com/mrdoob/three.js/blob/dev/LICENSE).
8. **Chrome Long Animation Frames and GoogleChrome web-vitals** provide different models for performance evidence. Chrome shows a supported-entry check and a `PerformanceObserver` for slow frames. `web-vitals/src/onINP.ts` illustrates how a real interaction metric uses observed browser events, groups events by interaction, and accounts for lifecycle. Start with separate measurements for a scripted interaction and a bounded list of slow frames. A bridge round-trip includes capture and transport time, and a short scripted run does not represent real-user INP or population performance. Also record HTTP error status separately from transport failure. [Observer example](https://developer.chrome.com/docs/web-platform/long-animation-frames), [web-vitals source](https://github.com/GoogleChrome/web-vitals/blob/main/src/onINP.ts), [request lifecycle and HTTP errors](https://playwright.dev/docs/api/class-request), [DevTools performance reference](https://developer.chrome.com/docs/devtools/performance/reference/).
9. **axe-core and Pixelmatch** offer two independent checks that can complement Taro's audit. Axe's `axe.run()` examples cover scoped checks and results requiring manual review. Playwright's menu example first opens the state and checks that it is visible, then scans that state. Pixelmatch's README and `index.js` show a same-size image comparison with a per-pixel threshold and visible difference output. Playwright's visual comparison guide explains stabilizing captures and matching the baseline environment. Adapt a state-aware scan and a baseline/current/difference viewer. Manual keyboard and usability review still matters, and low pixel drift is no substitute for judging design quality. Verified MPL-2.0 for axe-core and ISC for Pixelmatch. [Axe API examples](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md#section-3-api-reference), [Playwright accessibility examples](https://playwright.dev/docs/accessibility-testing), [Pixelmatch implementation](https://github.com/mapbox/pixelmatch/blob/main/index.js), [visual comparisons](https://playwright.dev/docs/test-snapshots), [axe license](https://github.com/dequelabs/axe-core/blob/develop/LICENSE), [Pixelmatch license](https://github.com/mapbox/pixelmatch/blob/main/LICENSE).

## Implementation sequence

### 1. Let the agent use the same browser as the reviewer

Add agent actions for hover, click, scroll, drag, text, and keys. Let the agent target an observed element or specify a point on the visible page for a canvas interaction. Resolve the element again at action time and return a clear result if it moved out of reach, disappeared, or has ambiguous matches. Use the same input path for scrollable containers, keyboard modifiers, and drag gestures in the Prototype canvas and agent tools. Return the resulting screenshot, focus, scroll position, or navigation change so the agent can tell what happened.

Start at `scripts/review-browser.mjs`, `src/lib/review-browser.ts`, `src/lib/review-tools.ts`, `src/lib/review-tool-definitions.ts`, and `src/components/review-browser-canvas.tsx`. Keep explicit target and revision checks when switching between live and saved views. Test on a menu that opens on hover, a nested wheel-scrolling panel, a slider or sortable card, and keyboard focus that moves both ways with Tab and Shift+Tab. A canceled drag should release the button and leave the next action usable. Taro should report an ambiguous target or unsupported native dialog and leave the page state understandable.

### 2. Save the view that supports a finding

Offer three capture choices in the existing Review workbench and agent tools. Capture the visible screen, the whole currently rendered document, or the selected component. Save an explicit capture to the source revision with the viewport, device scale, scroll position, bounds, environment, and time. Keep claims about below-the-fold content tied to what was actually rendered. For lazy or virtualized content, the reviewer can scroll the relevant path and save additional evidence. For oversized captures, return a clear limit or visible subset with its bounds.

Depend on the existing scoped revision store and extend its evidence handling after measuring image payloads on both transports. Verify an offscreen heading on a long page, a component after scrolling, a hidden component that reports its state, and a mobile capture at a different scale. Reload the chat and reopen the exact saved capture. Opening a new revision should leave the historical evidence available on its original revision.

### 3. Replay the steps and show the motion

Save short named sequences such as “open menu, tab to account, expand account.” Start replay from a defined viewport, theme, motion preference, and stable test data where available. Save snapshots before and after meaningful steps, stop at the first unmet expectation, and show the failure next to the evidence. Keep live and replay targets separate so playback does not disturb an in-progress review. For CSS motion, add start, midpoint, and end checkpoints from browser animation timing. For a scroll-linked effect, capture named scroll positions. For unfamiliar canvas and WebGL effects, show the observed filmstrip and describe the observed timing. Allow exact scene checkpoints for authored demos after the project supplies a render-at-state hook.

This depends on browser actions, durable capture, and routing browser events by target session. An initial recording can consist of a bounded filmstrip for visual inspection. Evaluate downloadable clips separately after testing recording support, media storage and cleanup in the packaged app. Restore paused animations and stop recording when a step fails. Verify a menu transition, a scroll-linked effect, a WebGL or canvas scene, a replay with a broken selector, and an interrupted capture. Identify whether a frame was observed live or captured at a controlled checkpoint, and report unavailable rendering support. Where a story types a value, supply it from a test fixture or prompt at replay time so the recording can omit private entry text.

### 4. Explain what failed during the review

Show warnings and errors from JavaScript, failed or HTTP-error requests, and slow-frame observations alongside the step where they occurred. Subscribe before navigation or the action. Keep short bounded records by target and navigation, with time, severity, status and a sanitized URL where available. Default to summaries that exclude cookies, authorization headers, request bodies, typed text, and URL query values. Expose a separate performance trace when an engineer needs to investigate the cause of a slow step. Keep lengthy runs cancellable and avoid holding the existing 45-second request open for a whole recording.

This uses the browser event routing from the preceding step. Verify with fixtures that throw a script error, issue a request that returns 404, fail to connect, and block the main thread. A run with missing browser support, no relevant interactions, or a truncated observation window should describe which evidence was unavailable. Label results as lab observations and preserve browser version and relevant test settings.

### 5. Add focused accessibility and visual comparisons

Keep the current responsive and theme audit. Add the option to check a captured state such as the open menu, expanded disclosure, or focused control. Show automated accessibility findings and items that need a human check for visible focus, keyboard sequence, or content meaning. When comparing to a chosen baseline, show the current screenshot and highlight changed areas alongside it. Use the same browser environment, viewport, font availability, scroll position, and interaction state. Make masked content visible in the comparison settings and keep the original capture accessible.

This depends on saved state capture and repeatable setup. Trial axe-core and Pixelmatch in the existing verification harness before choosing shipped dependencies. Verify an unlabeled control and a keyboard trap that requires manual testing, a deliberate spacing regression, a font or environment mismatch, and a baseline update that leaves old revision evidence available. Check the real Chromium helper, Review UI, and native transport before treating packaged behavior as verified. Existing entry points include `node --test scripts/review-browser.test.mjs`, `node scripts/review-ui-check.mjs`, `node scripts/artifact-review-ui-check.mjs`, and the native stdio test documented in [Review mode](A:/taro/docs/review-mode.md:93).

## Decisions to validate during implementation

- Start with the existing bridge. No browser package swap is needed for the first two steps. Decide after a packaged test whether video should use an installed browser feature, an encoder, or the filmstrip alone.
- Keep images, logs and any media bounded. Confirm the largest evidence sizes both transports and both storage implementations handle before settling capture and clip limits. Use revision metadata and an evidence reference for larger media rather than embedding video in session JSON.
- Run deterministic stories first on supplied HTML and controlled local fixtures. On a live URL, record enough identity and environment to reproduce the attempt and mark visible changes in remote data or resources. A missing action, measurement, or frame should appear in the report with the reason.
