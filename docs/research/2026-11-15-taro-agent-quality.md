# Making Taro’s design jobs more reliable

Checked 15 November 2026. This is research for Taro’s existing runtime. The linked examples were read in source. Provider calls, benchmark runs, and the proposed changes were outside this research pass.

## 1. Check what the selected model can do before a design job starts

Taro currently checks that Designer, Code, and Type & QA each have an enabled model, and that Code can write. The request layer supports Chat Completions and Responses and can transport images and tools. That proves the adapter can express the request. A given endpoint, account, model, or combination of features can still fail. `SubmitDesignHandoff` also advertises an open `artifact` object while `parseDesignSubmission` performs stage-specific validation downstream. [Role checks](A:/taro/src/lib/professional-runtime.ts:631) · [Streaming adapter](A:/taro/src/lib/model-stream.ts:7) · [Submission parser](A:/taro/src/lib/design-job.ts:54)

- Record separate checks for image reading, streamed tool calls, and structured results for the actual endpoint, protocol, model, and credential profile. Keep official provider claims and locally verified results distinguishable. For an unknown compatible gateway, offer a Models settings check with a small synthetic image that has a distinctive answer, a harmless local tool whose result must be returned to the model, and a schema-validated response. Test the combination the role will use. This verifies basic capability through Taro’s request path. Use the pilot in section 5 to test visual judgment and reasoning quality. Keep timeouts and credential failures distinguishable from unsupported features, and recheck on configuration change.
- Require streamed tool calling and a valid handoff where the workflow depends on them. Use image input for the Designer when the brief uses visual evidence and for QA when judging screenshots. State which role cannot perform the visual step and keep automated browser findings available when a visual judgment cannot be made. Prefer explicit stage-specific tool schemas where the provider contract supports them. Continue to validate all handoffs locally, even when the provider reports strict schema support. A separate provider-enforced response schema can be an optional route for stages that need free-standing structured outputs.
- **Code to study.** OpenAI lists endpoint and feature support separately per model. Anthropic’s TypeScript `Models.retrieve` exposes model capabilities and alias resolution, and its API reports separate image input and structured output flags. The Anthropic metadata example is a pattern for providers that publish capability data and does not imply that Taro’s two current OpenAI-compatible protocols include Anthropic Messages. OpenAI’s Node example shows `responses.parse` with a schema and consumption of `output_parsed`. Reuse the contract and parsing discipline through Taro’s adapter. [OpenAI feature comparison](https://developers.openai.com/api/docs/models/compare) · [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) · [OpenAI Node schema example](https://github.com/openai/openai-node/blob/main/examples/responses/structured-outputs.ts) · [Claude Models endpoint](https://platform.claude.com/docs/en/api/models/retrieve) · [Anthropic TypeScript SDK](https://github.com/anthropics/anthropic-sdk-typescript/blob/main/src/resources/models.ts)

**Acceptance.** A text-only model can still answer a text chat and gets a clear explanation before a screenshot-dependent job. An endpoint that accepts images but drops them fails the synthetic image check. Tool calls and tool-result replay work through both protocols. A response that renames, omits, or invents a required handoff field cannot advance the stage.

## 2. Give every stage the brief, approvals, and visual references it needs

Taro persists the design intent, plan path, preview revisions, and QA verdict. It checks the actual plan text against the native preview during approval. The stage relay then builds a fresh model prompt from selected job fields. At job entry the ADI run is prepared with `referenceIds: []`, while a child’s tool-read image is added to its own message history. `boundedModelContext` keeps tool exchanges together and prioritizes recent history within a 64,000-character heuristic. It can omit older image exchanges. ADI already binds completion to the current workspace, fingerprint, contract, revision and evidence, so a design memory layer can reuse these identities. [Job record](A:/taro/src/lib/design-job.ts:23) · [Job setup and stage handoff](A:/taro/src/lib/professional-runtime.ts:647) · [Native plan approval](A:/taro/src-tauri/src/session_tools.rs:345) · [Context trimming](A:/taro/src/lib/model-context.ts:6) · [ADI completion](A:/taro/src/lib/adi/completion.ts:13)

- Save a small job record with the brief, the reviewed plan content or immutable reference and digest, the real approval receipt, design tokens and constraints, approved reference and asset IDs, key critique, and source revision. Store visual files and screenshots in the existing scoped stores. Record which asset is approved, which is inspiration, and which is current browser evidence. Add a revision and a content hash where available. Rebuild each stage’s prompt from that record, with selected current image bytes where required. Build the critical stage context after trimming casual history, while still counting both text and media against the model budget. Pass a full view for composition and a relevant crop for local issues when useful. [Image detail and request limits](https://developers.openai.com/api/docs/guides/images-vision#choose-an-image-detail-level)
- Resume through the existing version-checked job persistence and native approval path. Tie an approval receipt to the approved plan version and relevant reference versions. Treat updated files, references, or comments as changed inputs where they affect the assignment. ADI and browser audit evidence still need to match the current revision and contract. Record stage and tool outcomes so a restart can rehydrate missing inputs and reconcile an interrupted write. Taro’s ordinary child checkpoint already reports an uncertain tool outcome and tells the agent to inspect current state before retrying. Its design stages use job state, so carry the same principle into stage recovery. [Child recovery and tool checkpoints](A:/taro/src/lib/professional-runtime.ts:930) · [Job persistence](A:/taro/src/lib/professional-runtime.ts:664)
- **Code to study.** OpenAI’s TypeScript approval example holds a serialized run on the trusted side, binds the decision to its owner and request, and consumes it before resuming. Its in-memory map demonstrates the flow and explicitly calls for atomic durable storage in production. The Agents SDK handoff implementation exposes a deliberate history and context filter. Adapt this idea to Taro’s typed job handoff by selecting which facts and pictures each child needs. [Approval implementation](https://github.com/openai/openai-agents-js/blob/main/examples/docs/human-in-the-loop/server.ts) · [TypeScript handoff implementation](https://github.com/openai/openai-agents-js/blob/main/packages/agents-core/src/handoff.ts)

**Acceptance.** Run a long job with a reference image early in the chat and force trimming. Designer, Code, and QA can retrieve the correct approved reference, and QA can pair it with the assigned render. Close and reopen the app during approval and again after a saved candidate. No stage claims earlier approval for edited plan content, imports a visual from another workspace, or uses a successful audit to certify a newly changed source tree.

## 3. Compare saved revisions and stop when further work is unlikely to help

Taro already takes browser measurements at 393, 768, and 1440 CSS pixels, records an audit, requires QA to inspect the assigned revision, and allows one corrective Code pass. Earlier previews are preserved. The loop records the latest `code` as the current handoff and stops on verification or after the second attempt. Earlier review images help the user compare. They do not restore matching application source by themselves. [Revision loop](A:/taro/src/lib/professional-runtime.ts:760) · [Design job behavior](A:/taro/docs/design-jobs.md)

- Record each candidate with a recoverable source snapshot or checked patch, its preview and audit IDs, hard-check results, and specific open findings. Preserve both the current candidate and the best eligible candidate. Eligibility comes from current, same-source functional checks and ADI evidence. A visual preference can rank two eligible candidates. A candidate with an open blocker can be shown for review as incomplete. A candidate from a past source revision must be restored explicitly and verified again before Taro can call the workspace ready.
- Keep the existing initial build and one corrective pass for the first experiment. Give the correction only actionable findings with target, screenshot or DOM observation, severity, and what to verify. Stop when the current revision passes, the same failure repeats without progress, a hard regression appears, or a configured time/request budget expires. Measure whether a further pass ever helps before making it an option. If the new result regresses, the user can inspect the earlier candidate alongside the latest one and recover the earlier source through the appropriate workflow.
- **Code to study.** Design2Code feeds both the original target and the previous render to its visual revision function. Its experiment emits whole HTML with an older model. For Taro, pair those two views with verified browser findings and ask for changes to the existing source. The Self-Refine research implementation shows the generate → critique → revise loop and an attempt limit. Its acronym example accepts every nonnegative score as feedback input, so it does not implement a reliable best-candidate rule. Taro should let observed failures and acceptance evidence drive that rule. [Design2Code revision code](https://github.com/NoviScl/Design2Code/blob/main/Design2Code/prompting/gpt4v.py) · [Self-Refine paper](https://arxiv.org/abs/2303.17651) · [Bounded research example](https://github.com/madaan/self-refine/blob/main/src/acronym/run.py)

**Acceptance.** In a comparison fixture, a second attempt that improves the visual target but breaks a keyboard flow cannot displace the eligible earlier candidate. Both previews remain accessible. Repeated identical critique ends the attempt, and completion requires fresh evidence with all required findings addressed. Restoring an earlier source makes the next verification run against the restored tree.

## 4. Isolate a requested edit and watch for damage elsewhere

The native `Edit` tool already rejects missing or ambiguous matches unless multiple replacements were requested, and returns the before and after text. Review comment tasks already carry selector, original revision and scope. The existing browser suite exercises the comment workflow and narrow captures. [Native edit](A:/taro/src-tauri/src/agent_tools.rs:245) · [Comment tasks and saved revisions](A:/taro/docs/design-jobs.md) · [Current acceptance coverage](A:/taro/docs/adi/acceptance.md)

- Put the selected component, intended behavior, relevant files, and preserved behaviors in the edit brief. Use its current selector and revision to locate the right target. Let the existing `Edit` tool apply scoped changes, and give targeted comment jobs a changed-content check and a stale-base check. When a shared style or layout change is needed, include the neighboring components and viewports it can affect in the checks. Report the actual spillover if a requested change necessarily affects another surface.
- Verify both the changed behavior and nearby invariant behavior. Add stable screenshot comparisons for untouched regions and interaction tests for keyboard, focus, form or menu state as appropriate. Keep viewport, font, browser, theme and animation treatment consistent for visual checks. Treat pixel differences as a review aid. The requested update may intentionally change the baseline.
- **Code to study.** Aider’s edit block implementation separates parsing from applying bounded search/replace edits. It can search other in-chat files after a match fails, which is inappropriate for a Taro task pinned to a specific component or file. Playwright’s matcher waits for screenshot stability and preserves expected, actual and diff outputs. Taro can use this style in its existing browser tests. [Aider edit block code](https://github.com/Aider-AI/aider/blob/main/aider/coders/editblock_coder.py) · [Playwright screenshot matcher](https://github.com/microsoft/playwright/blob/main/packages/playwright/src/matchers/toMatchSnapshot.ts) · [Playwright visual comparisons](https://playwright.dev/docs/test-snapshots)

**Acceptance.** Fix one annotated card at the target widths. Its click and keyboard behavior pass, neighboring cards and navigation retain their behavior, unrelated snapshot regions stay within the agreed tolerance, and a stale anchor sends the task back to inspect the current component.

## 5. Find out which changes improve real Taro tasks

Use six website briefs and six 3D briefs for the first pilot, with three runs per brief in each condition. The website set can cover a build from an image, an approved brand asset, a narrow-screen fix, a keyboard interaction, a comment-linked edit, and a long job resumed after trimming and returning to a saved revision. Give the 3D briefs their own acceptance criteria for geometry and controls. Exercise at least one real provider through the Windows desktop. ADI’s documented frontend acceptance uses an offline fixture and calls out the unverified real-provider desktop flow. [ADI acceptance and current gap](A:/taro/docs/adi/acceptance.md)

- Run the current release and the proposed workflow on matched repository copies using the same briefs, visual references and viewports. Record hard checks per task, repeated trials on representative cases, acceptance rate, blind reviewer preferences with ties and swapped order, and reason for each loss. Review fidelity to the brief, visual hierarchy, responsiveness and preservation of unaffected parts. Use browser behavior and accessibility checks as separate required evidence. Keep a few fixtures aside while tuning.
- Record active time by stage, end-to-end time, wait time for human review, model requests, known usage by provider, and estimated cost per job and per accepted result. Use observed timing and a dated rate table. Mark missing usage as unknown. Where available, capture cached input and image-related usage using the provider’s reported categories to avoid double counting. Keep an actual runtime budget as well as measurements. Existing runtime and native ledger budgets are the starting point. [Current request and time budget](A:/taro/src/lib/professional-runtime.ts:712)
- **Code to study.** Design2Code publishes paired reference and render examples, human comparisons, and visual scoring code. Its screenshot-to-HTML task does not cover Taro’s keyboard interactions, persistent approvals or focused edit regressions. Promptfoo’s working model comparison config shows reusable fixtures, explicit checks, and cost and latency assertions; those assertions measure completed requests. Start with a local Taro runner around existing runtime and Playwright fixtures. OpenAI’s evaluation guide covers position bias and calibration of an optional automated judge against human agreement. The guide currently reports retirement of the hosted Evals platform, so its methodology is the useful reference here. [Design2Code study](https://arxiv.org/abs/2403.03163) · [Visual scoring implementation](https://github.com/NoviScl/Design2Code/blob/main/Design2Code/metrics/visual_score.py) · [Published dataset and human labels](https://github.com/NoviScl/Design2Code#data-and-predictions) · [Promptfoo model comparison config](https://github.com/promptfoo/promptfoo/blob/main/examples/compare-openai-models/promptfooconfig.yaml) · [OpenAI evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

**Acceptance.** Produce a baseline and candidate report with case-by-case renders, hard checks, reviewer votes, time and cost coverage. Choose whether to enable the changes from those results. Publish observed differences and ties for the pilot without generalizing a model ranking from a small sample.

## Suggested order

First capture today’s results and add the model check that prevents wasted runs. Then make approved references and decisions survive between agents and app restarts. Next make a correction stay within the requested area, verify it in the browser, and retain the earlier source when needed. Use the same small benchmark to decide whether the revised workflow should become the default.
